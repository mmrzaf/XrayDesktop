# Phase 3 — diagnostic engine and reports

Source preview `0.1.0-preview.3`; Xray baseline v26.11.9. The Phase 0–3 Windows compilation, native execution, real-core and GUI acceptance gates remain open until a Windows run produces evidence. This document is a source implementation and testing record, not a release certification.

## Scope and usage

Open the Diagnostics tab. The default group is Local; Run selected operates on one group (Local, Remote, Http, Socks5, Direct, PublicIp). Run all executes all required groups, respecting unchecked consent options. The main Cancel operation button cancels the suite. No probe is automatically run at application startup or periodically. Windows proxy activation continues to require explicit consent for a one-shot HTTPS request; that request now uses the configurable HTTPS destination and a separate fixed ten-second timeout. It does not run the diagnostic suite or a direct test. No diagnostic mutates Windows proxy settings or changes Xray routes. If the owned core exits during diagnostics, the session cancels the suite and attempts the existing recovery workflow after the active command unwinds.

Local results include path, result, elapsed time, detail, timestamp (hover), and fixed error categories. Native validation output stays in the bounded raw local logs. Missing prerequisites are skipped rather than silently replaced. A failed HTTPS request is not evidence of a particular server/protocol fault. Results are point-in-time, not health monitoring. Run all has 16 rows (D12 is three rows, D15 deferred). D11 references the same measurement as D08/D09; do not count it as an independent request.

## Network paths and safeguards

- `SocketsHttpHandler.UseProxy=false` for direct requests. Each proxied request uses a fresh handler and an explicit `IWebProxy` with `IsBypassed=false`, so localhost destinations do not bypass the explicit proxy. Proxy address must be an approved loopback HTTP or SOCKS5 endpoint. No proxy credentials, redirect following, cookies, decompression, or certificate-validation override. No implicit direct retry. Handler-level network behavior is tested separately from Xray routing; OS certificate/DNS machinery is not controlled by the application. This is not a leak-prevention system.
- Selected endpoint wins for its protocol. Otherwise a unique anonymous endpoint of that protocol can be tested, from the running configuration snapshot. Multiple ambiguous endpoints are skipped. If the explicitly selected endpoint is known authenticated, it is not silently substituted. Manual endpoint capability is verified by the actual request. Each proxied request checks live PID ownership before and after; ownership can still change between checks and TCP connection establishment. The selected path is used for IP comparison; when none is selected the unique HTTP endpoint is preferred, then SOCKS5. A proxy may use Xray's direct outbound depending on routing.
- Remote candidates are advisory; selected host/port is visible, manually editable and tested only with the direct consent checkbox. DNS and TCP use the OS path. When a profile changes or starts, the discovered targets refresh; an external edit while stopped may require Reload. Config or snapshot read failure does not suppress unrelated local diagnostics.
- HTTPS destinations must be absolute HTTPS URLs without userinfo or fragments. Default HTTPS: `https://www.gstatic.com/generate_204`; default IP service: `https://api.ipify.org`. Services can be unavailable; configure alternatives. URL query parameters are private. Explicitly saving destinations writes only URLs, timeout and schema version to `data/diagnostics.json` (plaintext, 16 KiB bounded read, atomic replacement). Bad settings are retained until an explicit save. Consent, remote target and results are not persisted. Default timeout 10 s, configurable 1–15 s for network probes; native version 10 s, validation 15 s; sequential suite 45 s cooperative deadline plus bounded native cleanup. Probes not reached before the suite deadline are skipped, active timed-out probes fail; cancellation marks remaining rows cancelled. Use selected groups if the total budget is insufficient. Synchronous OS calls cannot be forcibly cancelled, so the budget is not a hard real-time guarantee.
- HTTPS latency reads headers only; response headers capped at 32 KiB and drain size zero. IP bodies capped at 128 bytes and parsed as a plain address (IPv4-mapped IPv6 normalized). No unbounded download or redirect. TLS stays enabled, with normal platform trust.

## Report export

Preview / export report opens the exact JSON that can be copied or saved. Report schema 1 contains application and target-core versions, numeric detected core version when measured and safely parseable, OS version, fixed known IDs, enum paths/outcomes/codes, UTC timestamps and elapsed milliseconds. No raw result detail, URLs (including query strings and PAC), hostnames, addresses, public IPs, profile names/paths, PID, raw config, logs, UUIDs, tokens or credentials. This is allowlist reconstruction, not regex-only redaction. The preview is still metadata about your environment, so review before sharing. Optional selected log excerpts and disk logging remain deferred; raw log copy still requires a separate warning. No upload or telemetry.

## Automated checks

The default console runner now includes 19 additional Phase 3 checks (63 mandatory total), plus the existing five extracted-EXE smoke tests. All diagnostic network fixtures use loopback only. Coverage: known/unknown outbound shapes, ambiguous fields, URL and endpoint safety, handler settings, plain-IP parsing, sanitized report reconstruction, numeric version filtering, preference integrity, ambiguous endpoint selection, direct consent, already-cancelled suite, unowned listener, direct TCP, HTTP CONNECT rejection, SOCKS5 handshake rejection, cancellation during stalled proxy, refused proxy with a bound non-listening socket, self-signed certificate rejection without trust-store changes and typed error classification. HTTP/SOCKS refusal tests use a separately listening origin and require that no direct connection reaches it. No public service or private credentials are needed, and no actual Windows proxy is modified by Phase 3 tests. Optional existing real-core and WinINet tests remain separate. The native TLS test is expected to fail the request, not demonstrate successful trusted TLS or real remote connectivity. Execution pending.

## Windows acceptance (A12–A13)

1. Run the full pinned Windows build and extracted-EXE smoke tests. Confirm all 63 mandatory checks actually pass; investigate any platform/runtime difference, especially SOCKS5 handler behavior. Confirm the existing Phase 0–2 acceptance requirements separately.
2. With a trusted real v26.11.9 binary and test profile containing anonymous loopback HTTP and SOCKS inbounds, Run Local stopped, then Start and Run Local again. Verify state, listener ownership, raw logs, version and native validation (running snapshot, not edited source). Run D08/D09 individually through a known HTTPS destination; compare actual Xray log/routing observations. Repeat with a deliberately invalid remote or unreachable destination, incorrect port, TLS problem and an authenticated/ambiguous inbound. Observe Fail/Skipped instead of false green or direct fallback. Do not send private configuration to GitHub.
3. Run Direct and Remote with consent off and verify no public request. Enable consent only if acceptable; verify local DNS, TCP and direct HTTPS against the chosen destination. Exercise IP lookup with consent off/on and same/different output scenarios; confirm neither result is presented as a VPN guarantee. Test a redirect, oversized/non-IP body, timeout, and cancellation; verify GUI responsiveness. Kill the owned core during a test and verify prompt cancellation, restoration and cleanup; test close during an operation. Do this in a disposable Windows account if managing the OS proxy.
4. Use unique private fixture markers in a config, hostname, URL query, logs and public-IP detail. Preview and export; inspect exact JSON for absence of markers, paths and raw text. Confirm the export is valid JSON. Change probe preferences, restart, confirm URLs/timeouts persist but consent does not. Corrupt the preferences file and verify defaults, safe warning and original retention until explicit save.
5. Verify at 100/150/200% DPI and a small supported window. Phase 4 will refine layout/tray and packaging; Phase 5 requires end-to-end real Windows and VLESS acceptance. No stable release before those gates pass.

## Remaining limitations

No download-speed probe, selected raw log excerpts, disk log rotation, automatic monitoring, TUN, authenticated proxy support, watchdog or tray. Probe groups rather than arbitrary individual ID selection are provided. Successful HTTPS with a real Xray/VLESS profile, native Windows proxy restoration, GUI usability and the actual .NET build are not verified in the source-authoring environment (no installed SDK/PowerShell or accessible project repository). No changes to the original SDD or existing acceptance records are implied by this preview.
